# 紙面の安全余裕と、出力前の実測検査

更新日：2026-10-04。対象は202604と共通のプレビュー・記事単位PNG出力です。

## 現在の到達点

直下の `index.html` と `tools/build_article.mjs` は、同じ `preview/layout_safety.js` を使い、描画後の要素箱と文字行を検査します。プレビューの読込検査と紙面検査は別表示です。紙面の外寸が1456×2056であるだけでは、中の文章が収まっている証拠になりません。

必要な余白の初期値は28 CSS pxです。これは変更できる検査基準であり、任意の原稿や環境に対する安全性が証明された定数ではありません。旧号の `MEASURE_SAFETY_PX=28` と同じ数値でも、今回の意味と実装は別です。現行の制服名鑑は手組みの5ページで、旧号の実測パッケージ分割は使っていません。

この変更は本文・画像の採用・紙面CSSを変更しません。MarkdownからHTMLへの同期や自動改ページも追加していません。202603の原稿、固定HTML、既存PNGを変更・再生成していません。

## 余白の意味

基準にするのは、各 `.fixed-page` のborder-box外縁です。上・右・下・左それぞれについて、そのページに属する要素の矩形と、非空白テキストのRange行矩形までの最小距離を測ります。外へはみ出す場合は負になります。

「下297px」は、検査対象のうち最も下にある矩形から紙面下端までの距離です。本文の後に297pxぶん自由に追記できるという意味ではありません。枠の高さ、段組み、画像との関係、別要素との重なりによって、追加できる文章量は変わります。また、空の部分を含むコンテナーの箱も検査するため、視覚的な余白より小さく出ることがあります。

余白の変更は合否基準の変更です。紙面のpaddingを変えたり、文字を縮小したりはしません。28pxから80pxに変えて不合格になった場合、HTML/CSSの配置を別途直す必要があります。

ページ寸法・クリップ矩形の比較許容差は0.5 CSS pxです。指定した必要余白の下限には、この0.5pxを差し引きません。必要余白28pxに対して27.6pxを合格にすることはありません。

## 検査する内容

1. ページの外寸が1456×2056 CSS pxであることを確認します。

2. 要素箱が紙面外へ出ていないかを確認します。従来の旧号用検査にあった「24pxまでの紙面外を許容する」という扱いはしません。

3. テキストのRange行矩形を確認します。要素自身の幅や高さが正常でも、長い折返しなし文字列や固定高さの内部から文章がはみ出す場合を対象にします。

4. `overflow:hidden`、`clip`、`auto`、`scroll` の祖先による切れを確認します。静止PNGではスクロールして隠れた文章を読むことができないため、スクロール容器も対象です。回転・傾斜を伴うクリップなど、矩形だけでは厳密に判定できないものは検査範囲外として報告します。

5. 上下左右の最小余白を必要余白と比較します。どのページ・どの要素が不足しているかを返します。

6. `.fixed-page` 不在、エラーを示す代替ページ、画像の欠落や代替表示、読込中・失敗したフォント、未読込スタイルシート、実行中のアニメーション等を確認します。記事出力側ではさらに画像・フォント等の準備待ちとJavaScriptエラーを扱います。

画像の `object-fit:cover` は、指定された画像枠の内部で行う意図的なトリミングです。元画像のどの部分を残すべきかは自動判定しません。

## 合格が意味しないこと

検査の合格範囲は、現在の描画における要素箱と文字行の幾何です。

疑似要素、box-shadow、text-shadow、filter、outline、clip-path、mask、角丸の切抜き、SVG・canvasや画像内部の描画は、完全な描画範囲を測っていません。検査結果には注意事項を残します。元から使っている装飾を理由に全ページを一律でエラーにする代わりに、合格表示でもこの制約を明示します。

要素同士の重なり、文字と画像の意味の対応、原稿から内容が脱落していないか、最新Markdownと同期しているかは別の検査です。例えば、本文を削除すれば余白検査には通りやすくなりますが、記事の完成とは認められません。

背景画像やCSS内部の依存資産、まだ開始していない遅延処理、別のブラウザやフォントへ切り替えた後までの完全性も保証しません。プレビューは表示中の変化を継続監視しますが、将来の任意のスクリプト実行まで先に検査する仕組みではありません。

## プレビューで使う

CodeSwingでは従来どおりリポジトリ直下を既存Swingとして開きます。元の固定HTMLやCSSを保存し、入口の「保存後に再読込」を押します。

入口には「必要な余白」の入力欄、「要素・文字行の検査」の結果、選択ページの上下左右の残り余白、詳細欄があります。全記事内のいずれかのページでエラーが出た場合、合格表示にはしません。本文の読込が成功していても紙面検査は失敗することがあります。

倍率変更は従来どおり外側に適用されます。内部viewportは1456×2056を維持し、余白は拡大縮小前のCSS pxで表示します。検査表示・警告は紙面の外に置き、原本の文字位置や改行へ影響させません。

検査コードはHTML本文と同じWebview資産読取経路で読み、表示用のメモリ上の文書へ注入します。検査処理のコピーを記事ごとに置きません。

`preview/index.html` という別のPages用入口には今回統合していません。利用者のvscode.dev / github.devでの保存・再読込の実機合格も、HTTPや模擬の成功だけで認定しません。経路の違いは [12 プレビュー方式](12_preview_methods.md) を参照してください。

## 出力前に検査だけ行う

NodeとPlaywrightを実行できる環境では、次のコマンドで検査できます。vscode.dev単体にターミナルがあるという意味ではありません。

```bash
node tools/build_article.mjs 202604/01_王都女学院春の制服名鑑 --check-only --safety-px=28
```

検査だけの実行では、記事フォルダの `pages/`、`preview/`、`intermediate/` や原稿へ書き込みません。結果JSONと終了コードで判定します。詳細な引数・出力形式は [10 記事単位ビルド仕様](10_article_level_build_spec.md) を参照してください。

PNGを生成する場合も同じ検査を通します。検査失敗、読込失敗、代替エラーページを成功扱いで出力しません。検査を通った後に一時領域でPNGとmanifestを作り、全工程が成功してから既存出力を置き換えます。

この対策は記事単位の `build_article.mjs` に適用されます。旧号の一括export、従来の `preview.mjs` 経路、既存PNGをそのまま集める処理、EPUB全体の受入検査まで置き換えたものではありません。既存PNGの収集だけで、この検査を通ったと判断しないでください。

## 今回の現物確認

開始時masterは `817ee167c908a3422ff6225d085146d6b62c5454` です。この時点で202604の固定紙面HTMLは表紙と制服名鑑の2件だけで、計6ページでした。正本Markdownの改稿・画像追加が固定HTMLへ自動反映される工程はありません。

Linux、Chromium 133.0.6943.0、Playwright 1.60.0、viewport 1456×2056、DPR 1、screen media、OSの日本語代替フォントにNoto Sans CJK JP Regularを入れた環境で、既存HTMLを読んで検査しました。フォントは検査環境のみに配置し、リポジトリには同梱していません。ユーザーのWindows環境との一致試験ではありません。

初回の実測では、表紙の最小余白が約60.2px、制服名鑑全体の最小余白が約64.3pxでした。制服名鑑の下側の残りは、1ページ目から順に約297.0px、571.0px、571.0px、571.0px、1159.0pxです。いずれも要素箱・文字行についての値で、影や疑似要素は含みません。旧HTMLに余裕があることと、今後の原稿を流し込んだ紙面に余裕があることは別です。

再実行用の試験は [tests/layout-safety](../tests/layout-safety/README.md) と既存の [tests/preview](../tests/preview/README.md) を参照してください。紙面外20px、内部クリップ、長い折返しなし文字列、余白の境界値、動的な本文追加など、旧検査では見逃す反例も使います。

## 一定のバッファで保証できるところまで進める条件

固定の余白だけで、無制限の文章量や任意のフォント変更を吸収することはできません。余白に上限がある一方で、内容の高さには上限がないためです。余白を大きくしても、この関係は変わりません。

保証に近づけるには、先に変動する範囲を決めます。使用するフォントとブラウザ、文字サイズと行高、画像枠の寸法、見出し・キャプションの最大行数、利用できる装飾の種類と張り出し量を固定します。その条件で、内容の高さに装飾の張り出しと安全余裕を加えた値が、使用可能な高さ以下であることを確認します。

収まらない場合の動作も必要です。見出しと本文、画像とキャプションの関係を維持して次ページへ送るか、分割できる単位へ分けるか、作業を止めて修正箇所を報告します。`overflow:hidden` で消したり、原稿を黙って削ったりはしません。今回実装したのは、このうち実測と停止の工程です。

さらに強い条件へ進める順序は、次のとおりです。

1. Markdown正本から固定HTMLへの対応と同期判定を整えます。古い原稿の紙面が検査に通ることを、最新記事の完成と取り違えないためです。

2. 出力用フォント・ブラウザ・資産を固定し、プレビューと撮影が同じ準備完了条件を待つようにします。

3. 本文を置ける安全領域と、枠・柱・ノンブル・影等の装飾領域をテンプレートで分けます。装飾の最大張り出しを数値化し、今回範囲外の描画も検査対象へ取り込みます。

4. 超過した内容を意味のまとまりごとに次ページへ送る組版処理と、正本文字・画像の欠落検査をつなぎます。

5. 最終PNGを検査済みの成果物として記録し、そのPNGを最終出力へ使います。現在の画像主体EPUB方式なら、その先で本文が再改行される問題を避けられます。ただしPNGの生成時に切れを取り込んでいないことが前提です。

目標は、任意の入力を無条件で通すことではなく、条件内の紙面だけが検査に通り、条件外なら具体的な理由付きで止まる制作工程です。

## 計測APIの参照

テキスト行の矩形は [CSSOM ViewのRange.getClientRects](https://drafts.csswg.org/cssom-view/#dom-range-getclientrects)、フォント読込とレイアウトの待機は [CSS Font LoadingのFontFaceSet.ready](https://drafts.csswg.org/css-font-loading/#fontfaceset-ready) を参照します。いずれもその時点の状態を扱うAPIで、任意の将来の本文変更を先に保証するものではありません。
